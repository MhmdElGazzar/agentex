# AgenTeX Codex sequential test

When HEADED is explicitly requested, set `browserMode: "HEADED"` in the `host.js prepare` input. Otherwise HEADLESS is the default. For browser work, run `node <plugin-root>/scripts/codex/host.js preflight <runRoot> <assignmentId>` once per owned session before scenario actions. A nonzero preflight blocks browser execution. Route every subsequent browser command through `host.js browser <runRoot> <assignmentId> <playwright-cli-command> [args...]`; begin with `goto <target>`. Close through `host.js browser-close` after all actions. Never use raw `playwright-cli` for a Codex assignment.

You are the executor. Interpret the original prose using your reasoning; do not turn it into a regex or scripted action parser. Run scenarios one at a time. Do not spawn an agent or a Codex CLI worker.

1. Read `.agentex/codex.json` to find the plugin root. Read the original spec or ad hoc request and the relevant AgenTeX driver skills under `<plugin-root>/skills/`. Resolve environment, login mode, driver routing, and credentials using the existing `test-execution` conventions. Use `spec_drivers.js` for saved specs. No action may silently substitute for a specified interaction or assertion.
2. Before any driver action, write a temporary JSON input containing absolute `projectRoot` and `scenarios`. Each scenario has exactly one `spec` project-relative path or `adHoc` prose string and `requiredSteps`: every required interaction/assertion has a stable `id`, nonempty `assertionIds`, and `evidenceRequired`. Include `policy` if configured. The plan must capture all original obligations. Call `node <plugin-root>/scripts/codex/host.js prepare <input.json>`. Retain its custody output independently of the result you will write. The resulting source copies and assignment files are the authoritative inputs.
3. For browser work, use `host.js browser <runRoot> <assignmentId> <command> [args...]` for every Playwright CLI action; it supplies the assigned session ID and verifies the current launch. Save screenshots and logs beneath `sessionDir`. Use the browser-driver skill's snapshot, interaction, and verification procedure. Route `api:`, `db:`, `kb:`, and `ui-check:` to their existing drivers. Never improvise catalog entries. Multiple specs may share this one browser session, but keep each assignment and result separate.
4. Execute each required step and verify its expected result. Write one JSON result to its unique `resultFile`, following `<plugin-root>/scripts/lib/execution_result.md`. Populate every required step ID, assertion ID, ownership ID, evidence path relative to the absolute run root, and SHA-256 evidence hash. A product assertion failure is `FAIL`. Missing, ambiguous, or unexecuted work is `BLOCKED`. For `ui-check:` read `<plugin-root>/scripts/codex/ui-outcomes.md`: ask sequential NEEDS-USER questions before finalization, retain the original result, and use `host.js resolve` to record each answer and validated final result. A view mismatch stays BLOCKED with its named UI status. Use scenario counts, never step counts, in `summary`. When specs share a session, finish their sequential actions before closing that owned session once. Record verified cleanup in each result before finalization; never claim completion while the session is still open.
5. Call `node <plugin-root>/scripts/codex/host.js finalize <absolute-runRoot> <assignmentId>` once per result. Use its returned verdict and exit code as authoritative; never count a run as PASS from your own result alone. If the result is missing or invalid, report BLOCKED. Preserve the original frozen assignment and custody file. The unkeyed assignment digest checks accidental drift; an agent or caller with write access to both custody and assignment can still alter them, so this is limited custody, not authentication.
6. Standard reporting is mandatory for every run, including FAIL and BLOCKED. Record real ISO start/end timestamps and active durationMs (exclude human waiting) for the run and each scenario. Write report metadata JSON: `{ "run": { "startedAt": "<ISO>", "endedAt": "<ISO>", "durationMs": 0, "environment": "<name>", "loginMode": "fresh", "tools": {} }, "scenarios": { "<assignmentId>": { "startedAt": "<ISO>", "endedAt": "<ISO>", "durationMs": 0 } } }`. Replace example durations with observed durations; never fabricate timing or tool versions. Include observed versus expected behavior in each result step's `note`, without secrets. Call `node <plugin-root>/scripts/codex/host.js report <absolute-runRoot> <metadata.json>`. This revalidates every assignment, checks persisted validations, and produces schemaVersion 2 `run-summary.json`, `report.md`, `extent-report.html`, and authoritative `verdict.json`. Counts are scenarios; required-step coverage is separate. Use the report command's verdict and exit code for the final run. Reporting failure cannot PASS. Link all reports and evidence in the final response. Do not modify Claude execution files or invoke Claude CI.

## Shared instruction paths under Codex

For each shared driver skill, run `node <plugin-root>/scripts/codex/paths.js <absolute-project-root> <shared-skill-name>`. Substitute its `pluginRoot` for every `${CLAUDE_PLUGIN_ROOT}` reference and its `skillDir` for `${CLAUDE_SKILL_DIR}` in the shared instructions. These are path aliases, not Codex environment variables: do not assume Claude populated them. Quote resolved paths in shell commands. Resolve relative references against that shared skill directory. Use this host's assigned sessionId/sessionDir in place of the shared init_run.js session allocation; never start a second run tree or invoke Claude orchestration. All other driver, login, evidence and reporting obligations still apply. Keep secrets out of report metadata and step notes.
